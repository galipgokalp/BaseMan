# BaseMan Audit Report

Date: 2026-04-02
Scope: full-repo maintenance audit with production-risk priority, plus external dependency and documentation validation

## Executive Summary

BaseMan is still structurally viable, but it is carrying enough drift that it should not be treated as "warm standby" production software without a stabilization pass.

The strongest signals:

- Core local checks are partially healthy: `npm test`, `npm run lint`, and `node scripts/self-check-config.mjs` pass.
- The repo is not currently operating behind a trustworthy full quality gate. `npm run docs:links` fails heavily, and `npm run test:all` depends on a local server and external services.
- Production dependency drift is no longer small. `npm audit --omit=dev --json` reports 7 production dependency advisories: 6 high, 1 moderate.
- Multi-chain support exists in architecture and docs, but the shipped leaderboard UI is hard-wired to Base mainnet.
- Several contracts between docs, runtime, and APIs have drifted enough to create onboarding and maintenance risk.

Current recommendation: treat the project as "recoverable, but not maintenance-ready". Stabilize before feature work.

## Findings

### 1. High: Production dependency security drift is already material

Evidence:

- `npm audit --omit=dev --json` reported 7 production dependency advisories.
- High-severity packages in the resolved tree include `axios`, `h3`, `hono`, `lodash`, `picomatch`, and `socket.io-parser`.
- The application also shows version lag in core integration packages such as `@coinbase/cdp-sdk`, `@farcaster/miniapp-sdk`, `@farcaster/miniapp-wagmi-connector`, `viem`, and `wagmi`; see [package.json](/home/galip/BaseMan/package.json#L71).

Why this matters:

- BaseMan is network-heavy and API-heavy. Even when vulnerable packages are transitive, unreviewed drift in auth, request handling, or wallet integration stacks is operationally risky.
- This is the clearest signal that dependency maintenance has stalled long enough to become a production concern.

Recommended action:

- Create a bounded upgrade wave: patch/minor upgrades first for direct prod dependencies, then re-run audit and smoke flows.
- Record which advisories are truly reachable in BaseMan's runtime versus present in unused transitive paths.

### 2. High: Multi-chain positioning and shipped leaderboard behavior are inconsistent

Evidence:

- The repo documents Base mainnet and Base Sepolia support in README and architecture material; see [README.md](/home/galip/BaseMan/README.md#L110).
- The client leaderboard fetch is hard-coded to Base mainnet: `const leaderboardChainId = 8453;` in [src/leaderboard/api.js](/home/galip/BaseMan/src/leaderboard/api.js#L65).

Why this matters:

- This breaks parity between the documented multi-chain posture and actual shipped behavior.
- Any testing, QA, or staging exercise on Base Sepolia can silently look "healthy" while the leaderboard UI still queries mainnet.

Recommended action:

- Make leaderboard chain selection explicit and centralized.
- Decide whether the product is intentionally mainnet-only for leaderboard reads or genuinely multi-chain. Then align UI, docs, env, and tests to that decision.

### 3. Medium-High: The full quality gate is not hermetic and is unlikely to be reliable in routine maintenance

Evidence:

- `test:all` composes local checks, docs verification, contract tests, smoke tests, sponsor checks, and bundler checks in one script; see [package.json](/home/galip/BaseMan/package.json#L67).
- `scripts/self-check.mjs` assumes a locally running app at `http://127.0.0.1:5173`; see [scripts/self-check.mjs](/home/galip/BaseMan/scripts/self-check.mjs#L5).
- `docs:verify` includes `docs:links`, which performs live HEAD/GET requests across the docs corpus and fails on network/availability noise; see [scripts/docs-links.mjs](/home/galip/BaseMan/scripts/docs-links.mjs#L63) and [scripts/docs-links.mjs](/home/galip/BaseMan/scripts/docs-links.mjs#L103).
- Repo runtime expectation is Node `20.x`, while audit was performed under Node 22; see [package.json](/home/galip/BaseMan/package.json#L104).

Why this matters:

- A maintenance repo needs a deterministic "green means safe to continue" signal.
- Today the strongest all-in-one gate mixes local server assumptions, internet availability, and external platform stability.

Recommended action:

- Split checks into:
  - hermetic local gate
  - integration gate
  - external-doc validation gate
- Enforce Node version with `.nvmrc`, Volta, or CI pinning.

### 4. Medium: Documentation and API contract drift is now visible

Evidence:

- README describes `/api/miniapp-auth` as `GET`, but the implementation only allows `POST`; compare [README.md](/home/galip/BaseMan/README.md#L170) with [api/miniapp-auth.js](/home/galip/BaseMan/api/miniapp-auth.js#L17).
- README's API inventory does not mention `/api/ai-agent-webhook` or `/api/test-redis`; see [README.md](/home/galip/BaseMan/README.md#L163) and the actual `api/` file list.
- An older internal endpoint-analysis report is stale: it discusses a 13-function limit breach and endpoints that no longer exist, while the current top-level `api/` directory contains 12 files.

Why this matters:

- New maintainers will trust the README first and make incorrect assumptions.
- Drift between docs and actual server behavior increases debugging time and raises change risk.

Recommended action:

- Rebuild the API inventory from code, not from prior reports.
- Mark internal/diagnostic endpoints explicitly as `internal`, `ops`, or `dev-only`.

### 5. Medium: Quick Auth verification failure paths are too chatty and network-heavy

Evidence:

- On JWKS verification failures, the code logs structured diagnostics and performs an extra fetch to the JWKS endpoint before returning; see [api/_lib/miniapp-auth-verify.js](/home/galip/BaseMan/api/_lib/miniapp-auth-verify.js#L72) and [api/_lib/miniapp-auth-verify.js](/home/galip/BaseMan/api/_lib/miniapp-auth-verify.js#L85).
- Similar fallback logic repeats for remote-verifier failure handling; see [api/_lib/miniapp-auth-verify.js](/home/galip/BaseMan/api/_lib/miniapp-auth-verify.js#L158).

Why this matters:

- During an auth incident, the failure path amplifies network activity and log volume.
- The logs are operationally useful, but the current behavior is expensive and noisy for a hot endpoint.

Recommended action:

- Reduce auth failure diagnostics to a sampled or debug-only mode.
- Avoid secondary network probes on every failed verification unless explicitly enabled.

### 6. Medium: Paymaster proxy has a small but real request-contract inconsistency

Evidence:

- Vercel config exposes `Authorization` in API CORS headers; see [vercel.json](/home/galip/BaseMan/vercel.json#L46).
- The paymaster proxy's OPTIONS response only allows `Content-Type`; see [api/paymaster-proxy.js](/home/galip/BaseMan/api/paymaster-proxy.js#L393).
- The handler later reads `authorization` and `x-api-key` request headers as overrides; see [api/paymaster-proxy.js](/home/galip/BaseMan/api/paymaster-proxy.js#L464).

Why this matters:

- Same-origin usage may hide this for now, but the endpoint's documented CORS behavior and actual preflight response are not aligned.
- This kind of drift becomes painful when support tooling, browser-based probes, or alternate hosts are introduced.

Recommended action:

- Align CORS preflight headers with actual supported headers, or remove header override support if it is no longer a supported path.

### 7. Medium: Several core modules have grown into high-friction maintenance units

Evidence:

- [src/onchain-client.js](/home/galip/BaseMan/src/onchain-client.js) is 2532 lines
- [api/leaderboard.js](/home/galip/BaseMan/api/leaderboard.js) is 1349 lines
- [src/settings-panel.js](/home/galip/BaseMan/src/settings-panel.js) is 1352 lines
- [src/profile-panel.js](/home/galip/BaseMan/src/profile-panel.js) is 843 lines
- [src/leaderboard-panel.js](/home/galip/BaseMan/src/leaderboard-panel.js) is 672 lines

Why this matters:

- These files combine orchestration, fallback logic, transport details, DOM/UI concerns, and observability.
- Large files are not automatically broken, but this size plus the system's runtime sensitivity means regression risk is elevated.

Recommended action:

- Do not start with a cosmetic refactor.
- First carve out seams around transport, state, and environment detection, then extract behavior in small verified slices.

### 8. Medium: Documentation link verification is currently noisy enough to block trust in docs automation

Evidence:

- `npm run docs:links` fails across many official sites and also against project URLs.
- The checker performs live network requests for the entire docs tree and treats any fetch error as a broken link; see [scripts/docs-links.mjs](/home/galip/BaseMan/scripts/docs-links.mjs#L45) and [scripts/docs-links.mjs](/home/galip/BaseMan/scripts/docs-links.mjs#L116).

Inference:

- Some failures likely represent genuinely stale links.
- Others are almost certainly availability, anti-bot, redirect, or transient network failures rather than true link rot.

Recommended action:

- Separate "known-good official domains" from strict link enforcement.
- Add retry/backoff, optional allowlists, and a way to report "unreachable" separately from "dead".

## Positive Signals

- Contract-version and EIP-712 config alignment checks exist and currently pass.
- The paymaster proxy already enforces a target/function allowlist and zero-value sponsored calls.
- The codebase contains useful internal reports and security notes that can accelerate stabilization once stale items are filtered out.
- The logger utility is stronger than typical legacy game/web3 projects and gives a reasonable base for cleanup.

## Recommended Remediation Roadmap

### 0-2 Weeks: Stabilization

- Pin runtime to Node 20 in local and CI workflows.
- Triage production dependency advisories and land the safe patch/minor upgrades.
- Fix the documented/API drift around `/api/miniapp-auth`.
- Decide and document leaderboard chain behavior.
- Split quality gates into hermetic vs integration vs external-doc classes.

### 2-6 Weeks: Risk Burn-Down

- Reduce auth verification failure-path logging and extra network probes.
- Normalize paymaster proxy request contract and preflight behavior.
- Rebuild API and operations documentation from current code.
- Mark internal endpoints and internal reports clearly to reduce stale guidance.

### 6-12 Weeks: Maintenance Recovery

- Break down `onchain-client`, `leaderboard`, and panel modules behind narrow interfaces.
- Add higher-value integration tests around score signing, leaderboard reads, and MiniApp auth.
- Revisit docs automation so it can run reliably in CI without high false-positive rates.

## Suggested Next Actions

If work starts immediately, the highest leverage order is:

1. Dependency upgrade and audit cleanup
2. Leaderboard chain decision and alignment
3. Quality gate separation and runtime pinning
4. API/docs inventory refresh
5. Controlled extraction of `onchain-client` and `leaderboard`
